# Persona Pool — section plan

Status: **all three components implemented (2026-08-29)**.
The "PersonaPool" generation method in the Gradio UI (`app.py`'s
`persona_method` Radio) now calls a real GitHub-backed pool lookup
(`services/persona_service/github_pool.py`, `POST /v1/personas/pool-lookup`)
instead of the external DeepPersona experience Space stand-in described
below (`generate_persona_from_deeppersona` has been deleted). The pool repo
is [JsonLord/PersonaPool](https://github.com/JsonLord/PersonaPool), seeded
with 6 compiled bundled-example personas, and `.github/workflows/
persona-pool-generate.yml` (component B, `scripts/
generate_persona_pool_batch.py`) is wired to add live-generated diversity
on a daily schedule once its two required secrets are configured -- see
docs/aux-space-status-overview.md section -10 for what shipped, what was
verified live, and exactly which secrets remain the user's to add (I
cannot provision GitHub push credentials or copy a live model-router API
key into Actions secrets on anyone's behalf). The rest of this document is
kept as the original design record.

## 1. Motivation

Live TinyTroupe generation (`method == "TinyTroupe"`) is a real, model-backed call
per persona and, even after the concurrency/retry tuning in
`services/persona_service`, can take several minutes for a small batch and is
capped at `TINYTROUPE_MAX_PERSONAS` (default 3) per run precisely because nobody
should wait 10 minutes in a browser tab for something that doesn't need to happen
synchronously. Most requests don't need a *brand-new* persona anyway — they need
*a persona that fits the requested theme, customer profile, and behavior/ability
ranges*, which a sufficiently large, diverse, pre-generated pool can usually
satisfy instantly.

There is already dormant scaffolding for exactly this idea in `app.py`:
`POOL_REPO_NAME`, `POOL_PATH`, `get_persona_pool()`, `upload_persona_to_pool()`.
It currently points at an ad-hoc repo (`JsonLord/agent-notes`) and is inert on the
live Space because `gh` (the legacy GitHub client) is `None` there — GitHub write
flows were deprecated in favor of workspace-scoped control-plane storage. This
plan formalizes and replaces that scaffolding rather than resurrecting it as-is.

## 2. Component A — GitHub persona pool repository

A dedicated repository (not reused from unrelated ad-hoc storage) holding
generated personas as structured JSON, one file per persona, matching the
existing `SyntheticUserProfile` schema (`services/persona_service/models.py`):
`id`, `source`, `persona`, `abilities` (`AbilityProfile`), `behavior`
(`BehaviorProfile`), `generation` metadata.

Proposed layout:

```text
personas/
  <date>/
    persona_<uuid>.json        # one SyntheticUserProfile per file
  index.json                   # generated manifest: id -> {date, theme tags, summary stats}
README.md                      # schema version, generation provenance, how to regenerate
```

- `index.json` is regenerated on every write and is the only file the app needs to
  fetch to know what's in the pool without downloading every persona file — it
  should carry enough of each persona's `behavior`/`abilities` values and a short
  tag/theme summary to support the ranged-matching query in §4 without a second
  round trip per candidate.
- Personas are immutable once written (matches the existing "immutable run
  snapshot" convention used for session-scoped persona artifacts) — a bad
  generation is superseded by a new file, not edited in place.
- Retention: keep a rolling window (e.g. 90 days) pruned by a scheduled job, so
  the pool stays fresh (behavior/ability priors are generated by whatever model
  is configured at the time) without growing unbounded.

## 3. Component B — GitHub Actions daily generation workflow

A scheduled workflow (`schedule: cron`) that runs independently of the Space,
with no user waiting on it:

1. Checks out this repo (or a slim subset — just `services/persona_service` and
   its dependencies).
2. Runs the same `TinyTroupeGenerator`/`PersonaCompiler` pipeline already used by
   the live Space, against a **rotating set of themes/customer-profile
   archetypes** (e.g. e-commerce checkout, SaaS onboarding, support/contact
   flows, content discovery — broad enough that a later ranged-match query has
   something plausible to find) and a spread of explicit behavior/ability
   ranges (patient/impatient, high/low digital confidence, typical/non-typical
   vision, etc.), so the pool accumulates *diversity*, not just volume.
3. Uses the same `OPENAI_*` secrets already configured for the Space (the
   self-hosted router, or whatever is current at the time) — no separate
   credential to provision.
4. Commits the new persona files plus a regenerated `index.json` to the pool
   repo. A GitHub Actions job can run for the full ~10 minutes a real batch
   takes without degrading anyone's UX, since nobody is waiting on it.
5. Runs the retention prune from §2.

**Acceptance:** a scheduled run produces N new, schema-valid, distinct personas
committed to the pool repo with an updated `index.json`, without any Space
redeploy or user-facing wait.

## 4. Component C — in-app pool usage: closest-ranged persona group

Replace the current `PersonaPool`/DeepPersona-backed method (and, longer term,
offer this as a fast alternative even when `TinyTroupe` is selected) with a
lookup against the pool instead of a live generation call:

1. **Fetch**: read `index.json` from the pool repo (cached with a short TTL in
   the persona-runtime service, so a burst of requests doesn't re-fetch from
   GitHub every time).
2. **Score candidates**: for the requested `theme`, `customer_profile`, and
   optional explicit behavior/ability targets (the same sliders already exposed
   in Persona Studio — patience, irritability, risk tolerance, color vision,
   processing speed, etc.), score every pool entry by a combined distance:
   - **Textual/theme distance**: embedding similarity (reusing the same
     OpenAI-compatible endpoint's embedding capability, or a cheap
     keyword/tag overlap if embeddings aren't configured) between the request's
     theme/customer-profile text and the pool entry's theme tags/summary.
   - **Trait-range distance**: Euclidean or weighted L1 distance between the
     requested behavior/ability targets (where given) and each candidate's
     `BehaviorProfile`/`AbilityProfile` values, over the normalized `0..1`
     trait space already used everywhere else in this codebase.
3. **Select a group, not just nearest neighbors**: rather than returning the
   `count` individually-closest personas (which can all cluster near one point
   and defeat the purpose of testing with several distinct users), select the
   closest-ranged *group*: the smallest bounding range around the request that
   contains `count` plausible candidates, preferring a set that still spans
   reasonable diversity within that range (e.g. a light farthest-point/greedy
   diversification pass over the top-K nearest candidates) rather than `count`
   near-duplicates.
4. **Fallback**: if the pool has too few candidates within an acceptable
   distance threshold, fall back to live generation (`TinyTroupe`, still
   capped and warned per §1) for the shortfall, exactly as the existing
   `select_or_create_personas` pool-vs-create-new decision logic already does
   for the (currently GitHub-backed, currently offline-LLM-backed) pool
   mechanism — this plan's pool becomes the primary source that logic checks
   first, instead of the ad-hoc repo it targets today.

**Acceptance:** given a theme, customer profile, and optional trait targets, the
app returns `count` distinct pool personas whose combined behavior/ability
values bracket the requested range, in well under the live-generation wait, with
a visible indicator of which personas came from the pool vs. were freshly
generated to fill a shortfall.

## 5. Open questions to resolve before implementation

- **Pool repo ownership/location**: a new dedicated repo, or a directory within
  this repo? A separate repo keeps the Space's own deploy folder small and lets
  the Actions workflow have write access scoped narrowly, without touching this
  repo's own history.
- **Embedding availability**: `EMBEDDING_MODEL=text-embedding-3-small` is
  already configured in `config.ini`, but the current self-hosted router's
  `/v1/models` catalog (checked live during the provider switch) should be
  re-verified for actual embedding-endpoint support before relying on it for
  theme-similarity scoring; the keyword/tag fallback should be implemented
  regardless so pool matching works even without a configured embedding model.
- **Cache invalidation**: how often the persona-runtime service re-fetches
  `index.json` from GitHub vs. serving a cached copy, balancing pool freshness
  against GitHub API rate limits.
