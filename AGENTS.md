# Development Continuation Guide

## Approach

Treat `spec.md` as the architectural contract and deliver it in the numbered stages in section 29. Keep service implementations isolated: communicate only through versioned HTTP contracts, job IDs, and persisted artifact references. Preserve the legacy Gradio tabs while moving callbacks incrementally to `apps/gradio/api_client.py`; do not add new Jules-backed flows. Mark partial implementations explicitly with `PLACEHOLDER`.

- Three live-run defects are fixed. (1) `journey_finish` was rejected by schema validation because journeytest-core's director prompt never states the vocabulary `verdict.criteria[].result` accepts (`met`/`not-met`/`blocked`/`not-observed`) while telling the model to prefer the verdict *status* word "inconclusive"; `journeyContract()` now restates it on each criterion, the only hook `runJourney()` exposes. (2) Vision critique returned HTTP 413: full-page captures (2.4 MB / 12000px) were sent as raw base64 PNG, so the request body passed the router's cap; the producer now downscales to a byte budget and sends JPEG with a declared mime type, and the worker no longer retries statuses that can never succeed. - Live runs can now browse signed in, and their viewport is followed in real time. `runJourney()` already forwarded `statePath` to agent-browser as `--state`; `runWithJourneyTest()` now passes it from `sessionStatePath` (or `AGENT_BROWSER_STATE`) and reports `authenticatedSession` on the result. A configured path that does not exist fails the run rather than silently browsing anonymously. `services/journey-worker/node/src/viewportStream.js` pins agent-browser's WebSocket viewport stream to a known port and keeps the newest frame in memory, so `liveRunState` serves real frames instead of whatever screenshot the driver last wrote to disk, and viewers keep talking to the worker over HTTP -- which is what makes the live view reachable in the Space, where only one port is published.
- Browser credentials have a store and a settings dialog. `apps/api/credentials.py` keeps them per workspace and offers three sources, ordered by how much the service has to guard: a **reference** stores only the *name* of an environment variable (a Space secret), so nothing secret is written down and the value is read at run time; **state** is pasted storage-state JSON, encrypted at rest; **password** is a username/password for a future login-capture flow. Encryption fails closed -- without `AUX_CREDENTIAL_KEY` nothing secret is stored at all, because a credential store that silently degrades to plaintext is worse than one that refuses. Listing returns metadata only; the secret leaves the module in one direction, onto disk as an 0600 state file (opened with that mode, not chmod-ed after) for a run about to start. `apps/gradio/credentials_panel.py` renders the dialog and registers `store_browser_credential` / `list_browser_credentials` / `delete_browser_credential` as `api_name` endpoints, so the same three paths work from the Space API via gradio_client.
- A password credential can now be signed in and kept. `services/journey-worker/node/src/loginCapture.js` drives agent-browser to a sign-in page, fills the credential through batch-mode **stdin** (so the password is never in argv on a shared host), waits for the sign-in to land, and exports the session with `state save`. Two-factor authentication is why it waits rather than reports: a password alone does not finish a modern login, and the code comes from a phone. On detecting a challenge it extends once from the sign-in wait (`AUX_LOGIN_SUBMIT_WAIT_MS`, 20s) to a human-scale one (`AUX_LOGIN_2FA_WAIT_MS`, 3min), announces it exactly once, and continues on its own when the challenge clears -- a person answers it through the live viewport, whose stream accepts input events, so a headless browser on the server can still be typed into. Timing out on a challenge is reported distinctly from a rejected password, because the two need different reactions. Omitting the password drives nothing and only waits, which covers sites this cannot fill and cases where storing a password is not wanted at all. `CredentialStore.capture_session()` decrypts, posts once over loopback, and stores the result; the password stays inside that module and never reaches an error message.
- The live view shows the running browser twice, side by side: the whole viewport, and a 2.75x close-up centred on the pointer. At viewport scale a 22px marker over a small control is too coarse to tell a near miss from a hit, which is the thing a usability reader is trying to see. Both panes are the same frame -- the close-up is a percentage background-position crop of the image already on screen -- so it costs no extra capture, no second browser and no second stream, and needs no pane pixel size to position itself. With no pointer yet it says so rather than magnifying the middle of the page and implying the agent is looking there. `services/journey-worker/node/src/cursorKeeper.js` supplies the position by reading the on-page marker's own rect, so what the viewer magnifies is what the viewer can see. Init scripts being dead in 0.31.1 turned out not to matter: `eval` works, and agent-browser dispatches real `pointermove`/`mousemove`/`mousedown`/`mouseup`/`click` at the element it acts on, so the overlay follows the agent continuously rather than jumping between targets. Re-evaluated on a timer because a navigation takes the overlay with the old document.
- The browser can be handed to a person mid-run, for what an agent cannot finish: a second factor whose code is on someone's phone, or a bot challenge specifically asking whether a human is there. agent-browser's stream is bidirectional, so the worker relays the viewer's clicks and keystrokes down the socket it already holds -- verified against a real browser, which received a click at the exact coordinates sent. The viewer cannot connect directly because a Space publishes only one port and the stream's is not it. Handover is explicit and input is refused without it (`POST /v1/takeovers`, `POST /v1/input`): an agent mid-action and a person clicking are two hands on the same pointer, and the run is then evidence of neither. Every handover is recorded with its reason, URL and event count, because a step a person completed by hand is not a step the product afforded. A site with no credential registered can be signed into by hand (`sign_in_by_hand`): the page is opened, the person types their own username and password into the live view, and only the resulting session is stored -- no password is ever written down. **This does not make the browser look human.** Challenge scoring reads the client as much as the interaction, and this one is still CDP-driven; and Gradio has no pointer-move event, so a relayed click jumps rather than travels. It conveys human intent, not human movement.
- Verified against the pinned agent-browser 0.31.1 binary, not just its README: `AGENT_BROWSER_STREAM_PORT` is honoured, a connecting client starts frames, and the frame payload is `{type:"frame", data:<base64 jpeg>, metadata:{deviceWidth, deviceHeight, pageScaleFactor, offsetTop, scrollOffsetX, scrollOffsetY, timestamp}}`. **Init scripts do not work in 0.31.1**: neither `AGENT_BROWSER_INIT_SCRIPTS` nor `open --init-script <path>` runs the file -- a trivial probe never executed over http or file, by flag or env, in a fresh session -- and the binary has no `addinitscript` or `--extension`, though its README documents all three. That README describes a later build than the pinned one; check the binary's `--help` before relying on anything in it. `assets/cursor-overlay.js` is verified correct in Chromium (centres on the pointer, lands in captured pixels, survives navigation, does not intercept clicks) and is still requested, because it costs nothing and starts working the day the pin moves. Until then it reports `effective: false` rather than promising a cursor that never appears, and the pointer has to be drawn viewer-side from the run timeline.
